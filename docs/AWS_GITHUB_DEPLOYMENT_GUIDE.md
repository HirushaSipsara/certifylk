# CertifyLK AWS and GitHub deployment guide

This is the end-to-end operator runbook for connecting the existing CertifyLK repository to GitHub Actions, GitHub Container Registry (GHCR), AWS EC2, AWS Systems Manager, DNS, Nginx, and HTTPS.

It does not change the product. Readiness scoring, costs, AI validation, API routes, and the four-page workflow remain exactly the same.

> CertifyLK is a readiness-assessment tool. It does not issue, guarantee, or replace SLS certification or an official inspection.

## Important Free Plan limitation

An AWS Free Plan account is for evaluation and should not process sensitive data. During the trial, use the deterministic chilli-paste sample and synthetic evidence only. Upgrade deliberately to a Paid Plan and complete the privacy/retention review in `SECURITY.md` before accepting real business documents or photographs.

The Free Plan ends six months after account creation or when its credits are exhausted, whichever occurs first. Configure billing alerts before provisioning anything. A budget is an alert, not a hard spending cap.

## 1. What this guide creates

```text
Browser
  -> DNS A record
  -> Elastic IP
  -> EC2 security group: 80/443 only
  -> Nginx HTTPS container
     -> Next.js container
     -> FastAPI container
        -> PostgreSQL container and persistent volume
        -> persistent upload volume
        -> Gemini API, only when backend Gemini mode is enabled

GitHub push to main
  -> CI tests
  -> immutable GHCR images tagged with the tested commit SHA
  -> GitHub OIDC temporary AWS credentials
  -> AWS Systems Manager command
  -> EC2 deploy.sh
```

The EC2 host does not build the application. GitHub Actions builds both images. EC2 pulls the already-tested images, backs up the current state, runs Alembic and catalogue synchronization explicitly, starts the stack, and validates the public HTTPS endpoints.

## 3. Secure the AWS account and control costs

Do this before creating EC2 resources.

1. Enable MFA on the AWS root user.
2. Do not create root access keys.
3. Use an administrative IAM Identity Center identity or another non-root administrative identity for routine console work.
4. Open **Billing and Cost Management -> Budgets -> Create budget**.
5. Create a **Zero spend budget** using the simplified template.
6. Create a monthly cost budget, initially USD 25, with email alerts at 50%, 80%, 100%, and forecasted 100%.
7. Open **Billing -> Credits** and record the credit balance and expiry date.
8. Keep the deployment in one region: `ap-south-1`.

For the credit-conscious demonstration, start with:

- `t3.small`, Ubuntu x86_64;
- 30 GiB encrypted gp3 EBS;
- one Elastic IP;
- no NAT Gateway, load balancer, RDS, or additional EC2 instance.

`t3.small` has less memory than the preferred 4 GiB production baseline. It is suitable for a low-traffic demonstration because images build in GitHub Actions. Monitor memory and disk. Move to `t3.medium` before real traffic if the host is under pressure.

Do not select `t4g` for this workflow: it is ARM-based, while the current GitHub image build produces the default amd64 application images.

## 4. Create the EC2 Systems Manager role

In the AWS console:

1. Open **IAM -> Roles -> Create role**.
2. Choose **AWS service** as the trusted entity.
3. Choose **EC2** as the use case.
4. Attach the AWS-managed policy `AmazonSSMManagedInstanceCore`.
5. Name the role `certifylk-ec2-ssm`.
6. Create the role.

This instance role is only for the SSM-managed EC2 host. It is different from the GitHub OIDC deployment role created later.

## 5. Create the EC2 security group

Open **EC2 -> Security Groups -> Create security group** in `ap-south-1`.

Name: `certifylk-production-web`

Inbound rules:

| Type | Protocol | Port | Source |
|---|---|---:|---|
| HTTP | TCP | 80 | `0.0.0.0/0` |
| HTTPS | TCP | 443 | `0.0.0.0/0` |

Add equivalent IPv6 sources only if IPv6 will be configured completely. Do not add public ports 22, 3000, 5432, or 8000. Use Systems Manager Session Manager instead of SSH for host administration.

Keep the default outbound rule so the host can reach Ubuntu repositories, GHCR, GitHub, Let's Encrypt, AWS Systems Manager, and optionally Gemini.

## 6. Launch the EC2 instance

Open **EC2 -> Instances -> Launch instance** and use:

| Setting | Value |
|---|---|
| Name | `certifylk-production` |
| AMI | Latest supported Ubuntu Server 24.04 LTS x86_64 |
| Architecture | `64-bit (x86)` |
| Instance type | `t3.small` for demonstration |
| Key pair | Proceed without a key pair; use SSM |
| VPC | Default VPC or an existing internet-connected VPC |
| Subnet | Public subnet with a route to an internet gateway |
| Auto-assign public IP | Enabled for initial reachability |
| Security group | `certifylk-production-web` |
| Storage | 30 GiB gp3, encrypted, delete-on-termination deliberately selected |
| IAM instance profile | `certifylk-ec2-ssm` |
| Metadata | IMDSv2 required |

Add tags such as:

```text
Project=CertifyLK
Environment=production
Owner=your-name
```

Launch the instance and record its instance ID.

## 7. Allocate and associate an Elastic IP

1. Open **EC2 -> Network & Security -> Elastic IP addresses**.
2. Choose **Allocate Elastic IP address**.
3. Select the new address and choose **Actions -> Associate Elastic IP address**.
4. Associate it with `certifylk-production` and its primary private IP.
5. Record the Elastic IP.

An allocated Elastic IP can incur charges even when unused. Release it when the deployment is permanently removed.

## 8. Verify Systems Manager access

Wait several minutes after launch, then:

1. Open **Systems Manager -> Fleet Manager -> Managed nodes**.
2. Confirm the instance is online.
3. Open **Systems Manager -> Session Manager -> Start session**.
4. Select the instance and start a browser shell.

If it does not appear, confirm:

- the `certifylk-ec2-ssm` role is attached;
- the instance has outbound internet access;
- SSM Agent is running;
- IMDSv2 and instance metadata are reachable.

Ubuntu AWS images normally include SSM Agent. Check either service name:

```bash
sudo systemctl status snap.amazon-ssm-agent.amazon-ssm-agent.service || \
sudo systemctl status amazon-ssm-agent.service
```

## 9. Install Docker and host tools

Run the following inside the SSM session. These commands use Docker's official Ubuntu apt repository rather than the production-discouraged convenience script.

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl git jq certbot openssl

sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

. /etc/os-release
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: ${UBUNTU_CODENAME:-$VERSION_CODENAME}
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker version
sudo docker compose version
```

Create the dedicated deployment user and protected directories:

```bash
sudo adduser --system --group --home /opt/certifylk --shell /usr/sbin/nologin certifylk
sudo usermod -aG docker certifylk
sudo install -d -o certifylk -g certifylk -m 750 /opt/certifylk/repository
sudo install -d -o certifylk -g certifylk -m 700 /var/lib/certifylk/releases
sudo install -d -o certifylk -g certifylk -m 700 /var/backups/certifylk
sudo install -d -o root -g root -m 755 /var/www/certbot
```

Membership in the Docker group grants effective host-level privilege. Do not use the `certifylk` account as an application user or general human login.

## 11. Clone the repository on EC2

### Public repository

```bash
sudo -H -u certifylk git clone https://github.com/HirushaSipsara/certifylk.git /opt/certifylk/repository
```

If the directory was created earlier and is empty, the clone works. If it is not empty, remove only the empty directory after verifying it, then clone; do not overwrite an existing configured repository.

### Private repository

Create a read-only GitHub deploy key:

```bash
sudo install -d -o certifylk -g certifylk -m 700 /opt/certifylk/.ssh
sudo -H -u certifylk ssh-keygen -t ed25519 -N '' \
  -C 'certifylk-production-readonly' \
  -f /opt/certifylk/.ssh/id_ed25519
sudo cat /opt/certifylk/.ssh/id_ed25519.pub
```

Copy only the `.pub` value. In GitHub open **Repository -> Settings -> Deploy keys -> Add deploy key**. Name it `certifylk-production-readonly` and leave write access disabled.

Verify GitHub's published SSH host-key fingerprint before accepting it, then test and clone:

```bash
sudo -H -u certifylk ssh -T git@github.com
sudo -H -u certifylk git clone git@github.com:HirushaSipsara/certifylk.git /opt/certifylk/repository
```

Never copy the private deploy key into GitHub Actions or the repository.

## 12. Create the production environment file

On EC2:

```bash
cd /opt/certifylk/repository
sudo -H -u certifylk cp infra/production/.env.production.example infra/production/.env.production
sudo -H -u certifylk chmod 600 infra/production/.env.production
openssl rand -hex 32
sudo -H -u certifylk editor infra/production/.env.production
```

Copy the generated hexadecimal password directly into the protected editor. Configure:

```env
DOMAIN_NAME=app.your-domain.example
GHCR_OWNER=hirushasipsara
IMAGE_TAG=0000000000000000000000000000000000000000

POSTGRES_DB=certifylk
POSTGRES_USER=certifylk
POSTGRES_PASSWORD=PASTE_GENERATED_HEX_PASSWORD
DATABASE_URL=postgresql+psycopg://certifylk:PASTE_GENERATED_HEX_PASSWORD@postgres:5432/certifylk

AI_PROVIDER=mock
GEMINI_API_KEY=
GEMINI_MODEL=gemini-3.6-flash
ALLOW_AI_FALLBACK=false
```

Start with `AI_PROVIDER=mock` for the first infrastructure deployment. After the public sample workflow passes, switch to Gemini by editing only the EC2 file:

```env
AI_PROVIDER=gemini
GEMINI_API_KEY=YOUR_REAL_BACKEND_ONLY_KEY
GEMINI_MODEL=gemini-3.6-flash
ALLOW_AI_FALLBACK=true
```

Do not put the Gemini key in GitHub variables, GitHub workflow YAML, frontend environment variables, shell history, screenshots, or chat messages.

Check for unchanged examples without printing the complete environment:

```bash
grep -nE 'CHANGE_ME|REPLACE_|certifylk\.example\.com' infra/production/.env.production || true
stat -c '%a %U:%G %n' infra/production/.env.production
```

The expected mode is `600` and owner/group `certifylk:certifylk`.

## 13. Connect the domain to EC2

Use a domain you already own to avoid a new registration charge. Create an `A` record at the current DNS provider:

```text
Name: app
Type: A
Value: ELASTIC_IP
TTL: 300
```

For an apex domain, the name is commonly `@`. Do not add an `AAAA` record unless IPv6 is configured on the instance, subnet, route table, security group, and Nginx path.

If using Route 53:

1. Open **Route 53 -> Hosted zones -> Create hosted zone**.
2. Enter the domain and select **Public hosted zone**.
3. Copy the assigned Route 53 name servers to the domain registrar.
4. Add the `A` record pointing to the Elastic IP.

Domain registration is a separate annual charge and AWS promotional credits cannot be used for Route 53 domain registration.

Verify from the local workstation:

```powershell
Resolve-DnsName app.your-domain.example
```

Do not continue until it returns the Elastic IP.

## 14. Issue the first HTTPS certificate

The first certificate must exist before the production Nginx container can start.

On EC2, replace both values:

```bash
DOMAIN=app.your-domain.example
EMAIL=operations@your-domain.example

sudo certbot certonly \
  --standalone \
  --non-interactive \
  --agree-tos \
  --email "$EMAIL" \
  -d "$DOMAIN"

sudo test -f "/etc/letsencrypt/live/$DOMAIN/fullchain.pem"
sudo test -f "/etc/letsencrypt/live/$DOMAIN/privkey.pem"
```

If validation fails, check DNS, the Elastic IP association, security-group port 80, and whether another process is already using port 80.

## 15. Configure private GHCR access when needed

GitHub Actions uses its built-in `GITHUB_TOKEN` to publish the images. EC2 needs separate read access only when the GHCR packages are private.

Create a GitHub personal access token (classic) with only `read:packages`. If the organization uses SSO, authorize it as required. On EC2:

```bash
sudo -H -u certifylk editor /opt/certifylk/repository/infra/production/.env.registry
sudo -H -u certifylk chmod 600 /opt/certifylk/repository/infra/production/.env.registry
```

File contents:

```env
GHCR_USERNAME=your-github-user
GHCR_TOKEN=your_read_packages_token
```

The deploy script sends the token to `docker login` through standard input. The registry file is gitignored and is never injected into the frontend or backend containers.

If both GHCR packages are public, do not create `.env.registry`.

## 16. Create the GitHub OIDC provider in AWS

In AWS:

1. Open **IAM -> Identity providers -> Add provider**.
2. Provider type: **OpenID Connect**.
3. Provider URL: `https://token.actions.githubusercontent.com`.
4. Audience: `sts.amazonaws.com`.
5. Add the provider.

OIDC provides short-lived AWS credentials. Do not create AWS access-key secrets for GitHub.

## 17. Create the GitHub deployment IAM role

Open **IAM -> Roles -> Create role** and choose **Web identity** with the GitHub provider and `sts.amazonaws.com` audience. Name the role `certifylk-github-deploy`.

Edit its trust policy after replacing `AWS_ACCOUNT_ID` if required:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::AWS_ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:HirushaSipsara@127508250/certifylk@1324306736:environment:production"
        }
      }
    }
  ]
}
```

The subject is case-sensitive. It is restricted to this repository's `production` environment rather than all repository workflows.

Create and attach an inline permissions policy after replacing the region, account ID, and instance ID:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SendCommandToCertifyLKOnly",
      "Effect": "Allow",
      "Action": "ssm:SendCommand",
      "Resource": [
        "arn:aws:ssm:ap-south-1::document/AWS-RunShellScript",
        "arn:aws:ec2:ap-south-1:AWS_ACCOUNT_ID:instance/EC2_INSTANCE_ID"
      ]
    },
    {
      "Sid": "ReadAndCancelDeploymentCommand",
      "Effect": "Allow",
      "Action": [
        "ssm:GetCommandInvocation",
        "ssm:CancelCommand"
      ],
      "Resource": "*"
    }
  ]
}
```

Record the role ARN. Do not attach `AdministratorAccess`.

## 21. Run the first deployment

### Normal GitHub deployment

Push or merge to `main`. In GitHub Actions:

1. Open the `CI` workflow.
2. Confirm all four required jobs pass.
3. Open `Deploy production`.
4. Confirm both application images are published with the same full commit SHA.
5. Approve the `production` environment if approval is configured.
6. Confirm AWS OIDC authentication and the SSM deployment command succeed.

The workflow checks out the tested commit on EC2 and invokes `deploy.sh` using the same SHA.

If the very first automatic deployment runs before EC2 cloning, GHCR access, environment, DNS, or certificate preparation is complete, it will fail safely. Finish the missing bootstrap step and rerun the failed `Deploy production` workflow. Do not bypass CI or manually retag an image.

### Manual first deployment or recovery

Use this only after CI has passed and GHCR contains both images for the exact SHA:

```bash
cd /opt/certifylk/repository
sudo -H -u certifylk git fetch --prune origin

SHA=PASTE_FULL_40_CHARACTER_TESTED_COMMIT_SHA
sudo -H -u certifylk git checkout --detach "$SHA"
sudo -H -u certifylk env IMAGE_TAG="$SHA" bash infra/production/scripts/deploy.sh
```

Never deploy a shortened SHA, branch name, `latest`, or a commit whose CI failed.

## 23. Enable certificate renewal

After Nginx is healthy:

```bash
DOMAIN=app.your-domain.example

sudo certbot reconfigure \
  --cert-name "$DOMAIN" \
  --authenticator webroot \
  --webroot-path /var/www/certbot

sudo install -d -m 755 /etc/letsencrypt/renewal-hooks/deploy
sudo install -m 755 \
  /opt/certifylk/repository/infra/production/scripts/reload-nginx-after-renewal.sh \
  /etc/letsencrypt/renewal-hooks/deploy/certifylk-nginx

sudo certbot renew --dry-run
systemctl list-timers | grep certbot
```

Do not enable HSTS preload without a separate domain-wide review.

## 26. Rollback

An unhealthy deployment automatically restores the previous application images when a previous release is recorded. Database migrations are never automatically downgraded.

Manual application rollback:

```bash
cd /opt/certifylk/repository
sudo -H -u certifylk bash infra/production/scripts/rollback.sh
```

Explicit tested target:

```bash
sudo -H -u certifylk bash infra/production/scripts/rollback.sh FULL_40_CHARACTER_COMMIT_SHA
```

Use `BACKUP_AND_RESTORE.md` only when a data/schema restore is explicitly approved. Never run `docker compose down --volumes` in production.

## 27. Troubleshooting

### GitHub CI fails

- Open the failed job and fix the code/test issue.
- Do not deploy the failed commit manually.
- Rerun CI only after committing the fix.

### GitHub cannot assume the AWS role

- Confirm `AWS_ROLE_ARN` and `AWS_REGION` in the `production` environment.
- Confirm the trust-policy repository spelling, case, environment name, audience, and account ID.
- Confirm the deploy job has `id-token: write`.
- Do not solve this by creating permanent AWS access keys.

### SSM command fails or instance is offline

- Confirm the instance role includes `AmazonSSMManagedInstanceCore`.
- Confirm SSM Agent is running.
- Confirm outbound HTTPS access.
- Confirm the GitHub IAM policy references the exact region and instance ID.

### GHCR reports unauthorized

- Confirm both packages exist for the requested SHA.
- Confirm `.env.registry` is mode `600` and owned by `certifylk`.
- Confirm the classic token has `read:packages` and any required organization SSO authorization.
- Confirm `GHCR_OWNER` is lowercase.

### Nginx or certificate fails

- Confirm DNS resolves to the Elastic IP.
- Confirm inbound 80/443.
- Confirm the certificate directory exactly matches `DOMAIN_NAME`.
- Confirm no AAAA record points somewhere unconfigured.
- Run `sudo certbot renew --dry-run` after Nginx is healthy.

### Backend is not ready

```bash
cd /opt/certifylk/repository
sudo -H -u certifylk docker compose \
  --env-file infra/production/.env.production \
  -f infra/production/docker-compose.yml ps
sudo -H -u certifylk docker compose \
  --env-file infra/production/.env.production \
  -f infra/production/docker-compose.yml logs --tail=200 backend postgres
```

Check database readiness and migration output without printing environment variables.

### Host runs out of memory or disk

- Check `free -h`, `df -h`, and `docker system df`.
- Do not delete database or upload volumes.
- Remove only reviewed unused image layers or increase EBS deliberately.
- Upgrade from `t3.small` to `t3.medium` if sustained memory pressure is confirmed.
- Review backup retention and copy completed backups off-host before pruning.

## 28. Stop costs safely when the demonstration ends

Stopping EC2 stops compute charges, but EBS, snapshots, Route 53, domain registration, and an allocated Elastic IP can continue to cost money.

For a temporary pause, take a backup and stop the EC2 instance. For permanent teardown:

1. Take and export any required final backup.
2. Terminate the EC2 instance only after confirming the correct instance ID.
3. Confirm whether its EBS volume was deleted; delete only the exact obsolete volume if required.
4. Release the exact unused Elastic IP.
5. Delete obsolete EBS snapshots only after verifying retention requirements.
6. Delete the Route 53 hosted zone if it is no longer needed.
7. Disable domain auto-renewal separately if the domain itself is no longer required.
8. Remove the GitHub production environment/OIDC role only when deployment is permanently retired.

Do not delete the GitHub repository merely to stop AWS charges.
